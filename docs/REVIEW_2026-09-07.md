## Viewer 目录卡顿的定位证据

用户提供的 `10460103` 目录递归包含 6,446 张 HIF，照片在星级子目录中。实测扫描约 0.045 秒、逐文件缓存范围解析约 0.162 秒，主要阻塞不是扩展名扫描。

- 模拟旧目录仍有多个 HIF 批次读取时，主线程单张 `PhotoMetaDataProxy.read()` 等待共享 ExifTool 执行锁约 16.4 秒；无后台竞争时约 0.68 秒。
- 首张约 49.8 MP HIF 原先为生成小预览而在 GUI 线程完整解码 HEVC，`PreviewPanel.set_image()` 返回耗时约 1.49–1.56 秒。
- 修复后图片信息先用缓存，后台结果局部补齐；大 HIF 优先复用准确档位缓存，未命中时显示加载提示并异步解码。临时真实副本上 `set_image()` 返回约 0.0216 秒，约 1.94 秒后显示完整 8640 × 5760 图像。

这是本机、该样本的测量，不代表整目录加载固定耗时。正常小图、RAW 和按住方向键策略的回归均保留。真实图库排查采用读取，图像写入验证使用临时副本。

## 后续可单独推进的结构优化

1. **拆分共享文件列表的职责。** `_panel.py` 约 7,800 行，既包含缓存/导航，也包含文件事务与元数据应用。优先提取不依赖 QWidget 的事务和元数据状态逻辑，保留当前公开 API 和两应用的差异开关，利用已有失败注入回归保护行为。
2. **逐步让 BirdStamp CLI 与 GUI 共用导出作业构建。** 当前 CLI `render` 仍直接组合 helper，而 GUI 图片/GIF/视频走 `VideoFrameJob`。应先用同一组输入对齐默认输出，再迁移，避免新阶段只在 GUI 生效。此项本轮未改。
3. **评估大批量 GIF 的内存预算和流式编码。** 当前 Pillow 每个变体会保留全部采样帧。后续可基于编码尺寸和帧数估算内存，再选择分批/流式后端；应保留本轮修复的时间计划与所有变体一致性。此项本轮未改。

功能定位见 [Viewer 架构](../SuperViewer/docs/ARCHITECTURE.md)、[BirdStamp 架构](../SuperBirdStamp/docs/ARCHITECTURE.md)，必须保留的行为见 [AGENTS](../AGENTS.md)。
